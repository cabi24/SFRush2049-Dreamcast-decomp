## Established evidence

- **Resource bridge:** retail has 315 filename pointers at file `0xB44C0` / VA `0x8C0C44C0`, ending at file `0xB49AC` followed by zero. Every filename resolves to a disc file. All 315 MAT3 `gWaveFilenames` names/order and all 315 `gWaveSizes` values agree with DC filenames and decoded LZS/raw ROM sizes, verified against the original MAT3 ELF as well as reconstructed C. This anchors resource IDs, not payload equality or cross-platform struct layout. `texte.lzs` string is at file `0xA09B4`; `debugfonttex.lzs` at `0xA0A18`. Retail's 314 LZS resources all decoded successfully. `.ROM` is an asset extension; DC LZS is not MAT3's ZIP/DEFLATE path.
- **Prototype debug findings:** all four prototypes yielded **0 recovered formal symbol entries, type records or source-line records**, and no valid debug-bearing ELF/COFF, maps or object companions. February has 155 verified readable resource-name/filename pairs; April has 160, e.g. `kWaveTextE -> texte.rom`. Their indices differ from retail. August retains filenames without those readable `kWave...` tables. Diagnostics and `DEBUG`/`PATH EDITOR` text are useful search anchors, not formal symbols or proof of reachable developer menus. PlanetWeb filename/assert strings belong to browser code, not recovered Rush gameplay debug metadata. These are bounded static checks, not proof against every undocumented opaque format.
- **SDK clues:** Shinobi 1.68, Audio64 10.0.f.2 and Kamui2 16,3,4,0 identify linked SDK components, **not the gameplay compiler**. SDK and gameplay objects may have different producers. Hitachi-style ABI alone is insufficient: GCC 2.95.2 also supports `-mhitachi`.
- **MAT3 reference:** `C:\rush2049-mat3`, especially [HANDOFF.md](../rush2049-mat3/HANDOFF.md) and [current build report](../rush2049-mat3/decomp/build/2049LE/report.json). Reported baseline is **1,841/1,844 functions, 713,440/715,968 game-code bytes (99.6469116%), 146/148 C-configured units**. Root README/progress reflect an older 60.37% snapshot. Existing stored DOL verification passed with five documented GC exceptions; no fresh rebuild was done. Those exceptions do not transfer to DC. Original `rush_d.elf` is big-endian PPC with symbols/DWARF v1: 11,132 named ELF entries, 149 CUs and 37,095 line rows. These scopes differ from the 1,844 game functions. All 31 pinned MAT3 reference hashes remained unchanged after the pilot.

Reuse MAT3 names, types, algorithms and resource semantics as evidence. Recheck DC field widths/offsets, signedness, alignment, endianness, platform wrappers and floating-point behavior. PPC/N64 instructions and ABIs cannot transfer as SH-4 byte matches. GC rendering/input/GDFS shims and MSL inline math are not DC implementations.

## Blocker and concrete asks for Claude

No reviewed SH-4 compiler/assembler/linker, matching runtime/headers or known version/options configuration was located in the bounded search. Signed Microsoft LLVM 19.1.5 was found, but its registered targets are ARM/AArch64/x86, not SH. Search was scoped, not exhaustive.

Read-only **`C:\Windows\system32\wsl.exe --list --verbose` was denied**, exit1 `Wsl/E_ACCESSDENIED`. WSL contents remain unknown. Do not bypass, change security/system settings or repeat the denied operation without materially new authorization/evidence. This was a runtime denial, not an automatic approval-review rejection.

1. **Read/pin first:** read the pilot results/manifest and toolchain research. Verify the configured scratch executable hash; from `pilot`, run `python -B tools/validate.py`. Preserve current evidence and counters. Do not restart MAT3/N64 matching.
2. **Establish lawful tools:** locate a lawfully held period-compatible Katana/Hitachi SHC package or reviewed SH GCC/Binutils environment, with compiler, assembler, linker, headers/runtime and version/help documentation. Hash tools, record provenance/host requirements and verify SH-4/endian/object support. Do not download proprietary mirrors or install automatically. If unavailable, report the exact missing component/path and pause that lane.
3. **Determine compiler/version/options:** use the four training slots, with bsearch drift explicit. Build minimal DC declarations, not the whole GC header tree. Test signed/narrow returns, stack/callee saves, pointer/struct layout, division helpers, FP arguments/FPSCR/rounding and aliasing. Treat compiler families as hypotheses; record full argv, tool/source/header hashes, emitted objects and diagnostics for every trial.
4. **Validate byte ownership and linkage:** independently corroborate boundaries/delay slots; distinguish code from literal pools/padding. Validate typed relocation width/endian/target/addend, PC-relative reach, relaxation, shared pools, TU/section order and BSS/global initialization. Build a fixed-address mini-link with maps and compare code **and** dependencies, no arbitrary masks. Freeze the selected configuration using the external SHA256 pin before compiling held-out functions; do not tune against held-out results or replace the unresolved getter.
5. **Then expand with disjoint ownership:** after pilot gates pass, assign nonoverlapping functions/TUs and output directories; keep interp/enginetorque under one drivetrain owner. One integrator owns shared headers, pools, linker config and promotions. Record I/E/byte-exact/local/full-image states separately, with reproducible commands, hashes, fixtures, mismatch diagnosis and a drift ledger. No original-byte fallback counts as C progress.

**Stopping conditions:** at most 16 justified compiler/version/option configurations; after 16 or about two focused hours without a nontrivial exact local link, revisit compiler/ABI/source identity rather than brute-forcing flags. Park a function after three evidence-backed source-shape changes or 45 minutes without new strict equal bytes. Compiler/call-ABI failure stops that lane; isolated source drift parks that function. Expand only after at least five credible I/E results and three nontrivial exact local links spanning pointer/integer and FP behavior, including a held-out arithmetic/global case. Keep unresolved slots visible and shared bytes counted once. No full-image build or watcher is required for this next bounded stage.
