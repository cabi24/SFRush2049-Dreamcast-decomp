# Dreamcast reference survey: shots, battle, records, save and state

## Result

**Use MAT3 first for this slice, with N64 as a valuable cross-check rather than a replacement.** In eight deliberately selected functions, MAT3 has four practical wins, N64 has one narrow loop-structure win, and three are ties. This is a small, non-random sample, not a percentage estimate of whole-game ancestry or matching progress. The strongest discriminators are Dreamcast's FindWinner tie reset and SaveInit allocation/list policy. Much gameplay is shared. No reference supplies SH-4 compiler scheduling, correct Dreamcast offsets, or all Dreamcast platform behavior automatically.

## Concrete next-use recommendations

1. Start BattleDamage2 and FindWinner from MAT3, retaining DC offsets and target-tested branch policy. For BattleDamage try the existing native N64 helper as an alternate control-flow formulation, but preserve target store order and do not import N64 field offsets.
2. Treat AnimateCase and ProximityDamage as shared-gameplay algorithms. The real remaining gaps are DC emitted shape: the removal guard/pointer-addressing in AnimateCase and temporary layout plus multiply association in ProximityDamage. Neither port's ISA-specific shaping is a substitute for SH-4 verification.
3. Use N64's explicit 12×3×5 InitRecords loop as a compact structural reference, not as proof of broad N64 superiority.
4. Save/platform code needs per-function comparison: fixed limbo allocation favors MAT3 here, while DC VMU behavior and training records remain target-specific. Do not extrapolate SaveInit to all SaveServer/PS functions. D/save.c:51-99 currently scans eight slots and TRN records; M/save.c:89 onward scans four and is therefore not a safe platform template.
5. State transitions retain shared high-level logic, but N64 overlays/audio initialization and MAT3 empty overlay stubs are substantial platform divergence (N/state comments:2-44; M/state.c:25-28). Choose per branch against DC target, not by whole-file text similarity.

## Limitations

This survey did not rebuild any reference, test gameplay, or prove original C identity. Four shots are presently nonmatching in DC `build/report.json` (140/154/252/456 differing bytes respectively). These mismatch counts are not similarity scores between MAT3 and N64; address drift and compiler output can dominate them. Existing exact byte claims above cover only selected mapped spans, not adjacent pools or full functions with different symbol extents. Remaining unlocated N64 BattleDamage2 equivalent is an explicit search limitation. This documentation records the survey snapshot; it does not add matching credit.
